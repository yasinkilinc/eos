### Decided without asking

- D1: the per-agent baseline race is fixed by keying `_bash_changed`'s state on `hook.actor` rather than by taking `core/lib/lock.py`'s file lock around the session's state file. A lock would make two truly concurrent Bash calls in one session (main + subagent, two subagents) wait on each other for git subprocesses that have nothing to do with each other; keying by agent gives each agent stream its own independent baseline with no serialization and is provably correct for the failure mode N11/RVd actually named (a subagent's first call inheriting the main session's baseline). A lock would still be needed if two Bash calls from the *same* agent stream could race, which the harness does not do (one tool call at a time per stream).
- D1: `WORKTREE_SNAPSHOT_LIMIT=300` and the 4 MB per-file hash ceiling mirror `BASH_CHANGED_LIMIT`'s existing flood-protection shape (a fully-dirty repo or a huge generated file must not make one Bash call expensive) rather than introducing a second, differently-tuned constant.
- D1: a rename/copy's original path (the second NUL-separated field `git status --porcelain=v1 -z` emits for `R`/`C` codes) is consumed to keep the parse aligned but not recorded as its own snapshot entry -- the new path already appears as a normal entry, and treating the original path as a second "removed" path was tried and reverted: it doubled the event count for an ordinary rename with no new information (the new path's appearance already proves something changed).
- D2: pairs sharing a `commit_start` fall back to the old per-pair `touched_files` call rather than trying to disambiguate `git diff-tree --stdin`'s output some other way (e.g. de-duplicating requested pairs and fanning results out to every requester) -- de-duplication does not remove the actual ambiguity (two *distinct* end commits can still share a start, one empty, and `--stdin` still prints nothing for the empty one), so the fallback is the only shape that is provably correct, and the collision itself is rare enough (two different runs starting from the exact identical commit) that it costs almost nothing in practice.
- D2: `_foreign_files` (the per-pair function) keeps its own `git log start..end` subprocess rather than being rewritten to call `_commit_graph`/`_range_commits` for a single pair -- it stays the simplest possible reference implementation the batched path's tests check against, and a single-pair `git log` is already as cheap as this problem gets (the graph-building approach only pays off once it can amortize its one big query over many pairs).
- D2: `_batched_foreign` returns all-empty results immediately when `other_finish_commits` is empty, without ever calling `_commit_graph` -- matches `_foreign_files`'s own result in that case exactly (no commit can be "in" an empty set) and matches `change_capture_for_run`'s existing optimization of skipping the git-log call entirely when there is nothing to exclude.
