### Decided without asking

- D1: the per-agent baseline race is fixed by keying `_bash_changed`'s state on `hook.actor` rather than by taking `core/lib/lock.py`'s file lock around the session's state file. A lock would make two truly concurrent Bash calls in one session (main + subagent, two subagents) wait on each other for git subprocesses that have nothing to do with each other; keying by agent gives each agent stream its own independent baseline with no serialization and is provably correct for the failure mode N11/RVd actually named (a subagent's first call inheriting the main session's baseline). A lock would still be needed if two Bash calls from the *same* agent stream could race, which the harness does not do (one tool call at a time per stream).
- D1: `WORKTREE_SNAPSHOT_LIMIT=300` and the 4 MB per-file hash ceiling mirror `BASH_CHANGED_LIMIT`'s existing flood-protection shape (a fully-dirty repo or a huge generated file must not make one Bash call expensive) rather than introducing a second, differently-tuned constant.
- D1: a rename/copy's original path (the second NUL-separated field `git status --porcelain=v1 -z` emits for `R`/`C` codes) is consumed to keep the parse aligned but not recorded as its own snapshot entry -- the new path already appears as a normal entry, and treating the original path as a second "removed" path was tried and reverted: it doubled the event count for an ordinary rename with no new information (the new path's appearance already proves something changed).
- D2: pairs sharing a `commit_start` fall back to the old per-pair `touched_files` call rather than trying to disambiguate `git diff-tree --stdin`'s output some other way (e.g. de-duplicating requested pairs and fanning results out to every requester) -- de-duplication does not remove the actual ambiguity (two *distinct* end commits can still share a start, one empty, and `--stdin` still prints nothing for the empty one), so the fallback is the only shape that is provably correct, and the collision itself is rare enough (two different runs starting from the exact identical commit) that it costs almost nothing in practice.
- D2: `_foreign_files` (the per-pair function) keeps its own `git log start..end` subprocess rather than being rewritten to call `_commit_graph`/`_range_commits` for a single pair -- it stays the simplest possible reference implementation the batched path's tests check against, and a single-pair `git log` is already as cheap as this problem gets (the graph-building approach only pays off once it can amortize its one big query over many pairs).
- D2: `_batched_foreign` returns all-empty results immediately when `other_finish_commits` is empty, without ever calling `_commit_graph` -- matches `_foreign_files`'s own result in that case exactly (no commit can be "in" an empty set) and matches `change_capture_for_run`'s existing optimization of skipping the git-log call entirely when there is nothing to exclude.
- D3(a): `index.is_stale` reports only the sqlite index's own declared freshness key rather than inventing an equivalent for the brain/graph files, which declare none -- the task's own instruction ("if (a) has no deterministic definition... record that... rather than inventing one") applies file by file, not to the row as a whole; the index half is defined, the brain half is not, and only the defined half is implemented.
- D3(b): left undone rather than defining "a routing golden file configured" as a new convention (e.g. a fixed path under `docs/eos-evals/`) -- the task's condition names a configuration concept that does not exist in `RoutingConfig`, and adding one to satisfy a `consolidate` line would be a new feature decided on the engine's behalf, not the minimal, deterministic surfacing the task asked for.
- D4: the workspace-root line is printed for a procedure section only, not folded into every brief's own header (`EOS brief for this task -- {root.name}`) unconditionally -- the ambiguity C5c named is specific to a procedure's own step text (the only place free-text, non-`eos`-command relative paths appear), and printing it project-wide would repeat the same fact on every unrelated section (WRAPPERS, RELATED NOTES) that names no path at all.
- D4: the printed value is the workspace root's absolute path, not a path relative to the project (`os.path.relpath`, the shape `workspace.where`/`relocate` already use elsewhere) -- `relocate()` only rewrites literal `eos <verb> .` command lines and the header's own `— {name}`, never arbitrary prose, so a relative marker line would go stale exactly when the text is later relocated (moved to be read from a different cwd, e.g. the workspace root itself via `core/hooks.py`'s `home = workspace.of(root)` path). An absolute path reads correctly from any cwd the text ends up displayed from.
- RVg(1): the fix lives inside `index.is_stale()`, not in `consolidate.report()` or `cmd_consolidate` -- `is_stale()`'s own docstring already promised a pure read that only ever answers `None`/bool, so the bug was that function breaking its own contract, not a missing catch at some call site; fixing it there means every future caller (not just `consolidate`) inherits the safety, rather than each one needing to remember to guard it individually the way `cmd_query`/`cmd_impact` each separately guard `index.refresh()`.
- RVg(1): degrades silently (no stderr warning) rather than mirroring `cmd_query`'s "warning: answering from a possibly stale index" line -- `consolidate` already has an established idiom for a section that cannot be measured (`runs_unmeasurable`, `stale_notes` from an unreadable note, etc. all fold into counts or are simply absent, never a printed warning about *why*), and `is_stale` returning `None` already reads identically to "index never built," a case `consolidate` already treats as unremarkable. Adding a new warning channel for this one case alone would be new scope, not the fix the finding asked for.
- RVg(2): `WORKSPACE_PATH_MAX_CHARS = 400` truncates with an ellipsis rather than refusing to print the line at all -- a truncated-but-present path still tells a session "your steps run from somewhere other than here," which is most of the value; refusing outright on an edge case this unlikely (a real path over 400 characters) would lose that for no gain. 400 was picked generously above any realistic real-world path (typical OS ceilings run 1,024-4,096 bytes for the *whole* path, and a workspace root is rarely nested anywhere near that deep) while still being far below the task budget itself, so it can never be the dominant cost of a brief.
